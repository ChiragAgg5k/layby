Disposable sandboxes
from a mise.toml

Cloud agent products hand you someone else's environment on someone else's machine. This inverts it: the environment is a file in your repo, and the machine is whichever provider you point at.

View source How it works

The blueprint

It's just a mise.toml

[tools] and [env] are ordinary mise and work with a plain mise install on your laptop. The [sandbox] table is a namespaced extension that mise ignores.

One file configures your machine and the remote one. No Dockerfile per stack — the toolchain is the declaration.

Measured, not estimated

The image is the cache

Running mise install at boot costs minutes on every start — and real money on a metered provider. The toolchain is baked into an image at build time instead, so booting is a pull. The expensive install runs once per unique build definition, on whichever builder is cheapest.

Building in CI rather than locally is 4.6× faster than the same cold build on an M-series laptop — and free. The DigitalOcean figure is the honest end-to-end cost on real infrastructure: droplet provision (~45s), boot, then cloud-init pulling 154 MB and starting the container. Measured from a clean slate in blr1 on s-1vcpu-1gb at $0.0089/hr — that sandbox cost well under a cent. Once running, exec is instant: connections multiplex, so a burst of twelve commands reuses one TCP session.

DigitalOcean wins by some distance. Hourly billing makes a per-task sandbox cost a fraction of a cent, tags are first-class so reconciliation never leans on a naming convention, and keys attach per droplet. Render has no create-a-machine primitive at all — a sandbox there is a background worker, and every one of them is reachable by every SSH key on the account.

One gap is deliberate: there is no true in-sandbox self-destruct. Doing it properly means writing an API token onto a box running untrusted agent code, and a full-scope token is worse than an occasional orphan. cloud-init powers the droplet off at TTL, but that stops the workload, not the billing — layby down -expired is what stops the meter.

Load-bearing decisions

Every one of these was a bug first

Nine so far. These six changed the design rather than just the code — and the first was found only by running the thing on real infrastructure, not by any test that existed at the time.

01 — ISOLATION

Commands ran on the host

ssh concatenates its trailing arguments into one remote shell string, so bash -c "a; b" arrived as bash -c a; b and ran b on the droplet host. It failed quietly: the sandbox's jq 1.7.1 silently became the host's 1.6.

02 — READINESS

The poller DoS'd itself

The Docker image ships ufw 22/tcp LIMIT, rejecting an IP after six connections in thirty seconds. Polling every 250ms tripped it in two. The refusals looked exactly like a droplet that never booted.

03 — TRANSPORT

Multiplex, or lock yourself out

Every exec opened a fresh connection and hit the same limit after six commands — an agent running a handful of steps would be locked out of its own sandbox. One control master fixes it, and makes exec instant.

04 — CACHE KEY

Hash the whole build definition

Keying the image tag on the toolchain alone meant a corrected Dockerfile silently reused the stale image. The fix appeared to do nothing — twice — before the cause was obvious.

05 — PATH

Exported twice, on purpose

A login shell sources /etc/profile, which resets PATH and discards the image's ENV. Without both, run and shell disagree about whether node exists.

06 — TRUTH

The provider, not local state

~/.layby/state.json is a cache. A running sandbox with no local record is an orphan. Reconciliation is tag-scoped, so on an account with 402 droplets it sees exactly the ones it created.

Status

Where it stands

The Docker and DigitalOcean drivers are both verified end to end — provision, exec, env, exit codes, teardown. The Render driver is written but has never booted a sandbox: Render returns HTTP 402 until a payment method is on file, and background workers have no free tier.

Exit codes pass through, so an agent can run layby run $ID -- pytest and branch on $?. Progress goes to stderr; stdout stays clean.

Next lever on speed: a snapshot taken after the image pull would cut that 2m45s to roughly droplet-create time alone.
